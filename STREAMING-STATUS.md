# Streaming state

- Browser RAM limit is stored in the first-party `torfilms_ram` cookie (500–2048 MiB).
- `RetainedRamPool` retains original torrent pieces across player teardown/reconnect within the same document. The budget is shared across hashes. New pieces evict older pieces; lowering the budget can also evict. A page reload/navigation creating a new document releases the pool. Closed clients no longer seed their retained pieces until reattached.
- Browser discovery uses both the local tracker and public WebSocket trackers for non-private catalog sources. On 2026-09-07 `tracker.webtorrent.dev` accepted a WebSocket handshake from this host; the two older endpoints failed or timed out. A handshake does not prove that a particular torrent has remote seeders. STUN is already bundled; there is no configured TURN relay.
- Browser processing is now the default **experimental implementation**. `local-remux-worker.js` uses pinned Mediabunny 1.55.7 to demux original pieces and remux supported video plus the selected embedded/external audio into fragmented MP4. No encoder or bridge audio/seek-plan endpoint is used on this path. It retains native video controls, metadata duration, a common A/V presentation clock, keyframe seek preroll, and uses the existing RAM-backed verified torrent reader for both files. Subtitles still use the existing bridge conversion endpoint.
- `processing-mode` explicitly selects the old bridge compatibility path. Its generated MP4 bytes are **not** retransmitted through WebTorrent. Unsupported local codecs report an error, with no silent server fallback. AC3/DTS software decoding, local audio transcoding and video transcoding are not implemented.
- Local processing uses a module Web Worker and MediaSource. The worker parser caches up to 4 MiB per input; reads are requested in 256 KiB ranges. Output writes wait for browser append acknowledgment, playback pacing targets 20 seconds ahead, and old decoder ranges are removed. A 64 MiB unflushed-packet guard rejects oversized GOPs. These are separate buffers from the user's torrent-piece RAM budget; this is not a hard bound on total browser memory. Missing container duration requires cached metadata or explicit bridge mode.
- Worker termination cancels active piece readers on seek, track change, stop or unmount. Remuxed MP4 exists only transiently; original torrent pieces remain available for WebRTC upload. Availability of remote peers is not guaranteed.
- Cross-torrent audio substitution is not implemented. It needs explicit source/episode mapping and timing/version checks. The local remux path shares the same video torrent/hash regardless of the selected audio within that torrent.
- Season identifiers support numbers and strings (e.g. `Bonus`, `1.1`, `1.2 Бой камня`). Display titles and posters are independent season fields. Episode assignment and URLs use canonical string comparison.
- Public tracker reference: https://openwebtorrent.com/
- Mediabunny upstream/source and MPL-2.0 license: https://github.com/Vanilagy/mediabunny . The unchanged browser bundle and license are copied by `npm run build:p2p` and served locally (no runtime CDN).
- Validation authorized and performed: 59 automated tests, 58 passed, 1 existing native-RTC test skipped on Windows. Real worker tests generate media only in RAM, verify H264 B-frame decode cadence after a non-keyframe seek and selected AAC/external MKA/96 kHz 24-bit FLAC audio. Controller tests cover pause during loading, cancellation and end-of-stream; piece-reader tests cover boundaries, small-range lookahead, immediate use of successfully fetched pieces and shared demand throttling across 1000 tiny reads.
- In-app Chromium browser fixture successfully plays AAC and FLAC 96 kHz/24-bit and seeks to 23.3 seconds. Real Fate/Apocrypha BDRemux ED1 (1920x1080, ~24 fps, FLAC 96 kHz/24-bit) starts locally. Its repeated boundary stalls exposed missing lookahead for tiny demux reads and an unnecessary polling timer after successful HTTPS fallback; both are corrected. Android and arbitrary remote peer availability remain unverified.
- `flac-mp4-header.js` repairs the FLAC MP4 sample entry (channels, bit depth and representable divided sample rate) using unchanged STREAMINFO. This fixes Mediabunny 1.55.7's 16-bit/zero-high-rate entry without modifying the dependency or encoding audio. The source mapping is https://android.googlesource.com/platform/external/flac/+/refs/tags/android-14.0.0_r22/doc/isoflac.txt .
- Reproduce the local-only browser fixture with `node scripts/remux-browser-check.mjs` and open http://127.0.0.1:18189/ . It binds only loopback and generates its test video in RAM. It is not an online service or startup task.
- Follow-up live check: fixed a per-iterator demand throttle that generated a POST for every tiny demux read, starving the browser's HTTPS request queue. Throttle is now shared per file. HTTPS statistics expose request/body/hash/store stages. The actual BDRemux displayed ~23.7 fps after the fix. Cold pieces still require waiting on the upstream swarm; a sampled 29-second interval added only ~2.7 MB to a not-yet-full bridge cache. Continuous stall-free playback on that swarm has not been demonstrated; do not describe this as guaranteed by the software fixes.
