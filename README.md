# Torfilms

Torfilms — локальный RAM-first torrent video player. Приложение подключает magnet-ссылку или `.torrent`, выбирает видеофайл и отдаёт VLC/HTML5-плееру поток через HTTP Range requests. Piece store — ограниченный LRU-кеш в оперативной памяти; видеофайлы не сохраняются на диск.

Если в контейнере есть несколько аудиодорожек, Torfilms показывает их в селекторе «ОЗВУЧКА». Для MKV/AC-3 и других контейнеров, которые браузер может воспроизводить без звука, выбранная дорожка преобразуется в совместимый стерео AAC через `ffmpeg` pipe. Ни исходный файл, ни промежуточный результат не записываются на диск.

Для транскодируемых файлов используется собственная шкала полной длительности. После перемотки FFmpeg декодирует и обрезает обе дорожки до выбранного момента, затем кодирует видео в H.264 и звук в AAC. Это исключает сохранение предыдущего GOP только в видеодорожке. Независимое обнуление PTS/DTS удалено. Такой режим увеличивает нагрузку CPU и может быть тяжёлым для 4K; запуск совместимого видео с начала сохраняет копирование видеодорожки. В fullscreen управление накладывается поверх видео и скрывается после паузы курсора; движение мыши возвращает его.

## Запуск

### Hybrid-мост на компьютере

Добавлен выбор озвучек после выбора файла. Список получает ffprobe из RAM-потока
моста. При неподдерживаемом первом аудиокодеке предлагаемый совместимый режим
запускается автоматически; для остальных дорожек используйте «Включить выбранную
озвучку». Браузер проверяет canPlayType: AAC/MP3/Opus/FLAC в MP4 копируются при
заявленной поддержке, остальные преобразуются FFmpeg в AAC stereo. Видеокодек
никогда не перекодируется этим режимом. Проверка canPlayType предварительная:
поддержка конкретного профиля кодека и устройства может отличаться.

При выборе озвучки используется единый MP4-поток с аудио и видео через HTTPS,
а не раздельные несинхронные элементы. Этот поток не участвует в P2P-раздаче.
Кнопка «Исходный P2P-поток» возвращает торрент-поток с начала. Смена озвучки
сохраняет позицию через общий preroll; нижний ползунок использует полную длительность.
Встроенная шкала браузера для MP4-потока может показывать только полученный фрагмент.
Завершённые исходные pieces остаются в RAM, промежуточный MP4 идёт через pipe.
Для новой серверной части необходим перезапуск Hybrid-моста и обновление страницы.

Домашний вход к уже запущенному мосту: `powershell -File .\start-bridge-lan.ps1`.
Адрес по умолчанию http://192.168.0.122:18184/ (не старый порт 18182).
Вход передаёт HTTP и WebSocket-трекер на локальный 18183, без перезапуска моста.
HTTP позволяет проверить доступность страницы, но НЕ запускает браузерный P2P
на телефоне. Для него требуется доверенный HTTPS:
`powershell -File .\start-bridge-lan.ps1 -Address 192.168.0.122 -Certificate C:\path\cert.pem -Key C:\path\key.pem`.
Сертификат должен включать домашний IP в SAN и быть доверенным на устройстве
зрителя. Сертификат/корневой центр доверия автоматически не создаются и не
устанавливаются. Не обходите предупреждения браузера как замену доверенному TLS.

`npm run bridge` или `powershell -File .\start-bridge.ps1` запускает отдельную
страницу http://127.0.0.1:18183/ с локальным WebSocket-трекером. Существующий
плеер на 18181 не перезапускается. Введите magnet на странице моста: браузер
автоматически подключит этот же торрент на мосте. Обычные TCP/uTP-пиры снабжают
мост кусками, браузеры получают их по WebRTC и могут раздавать друг другу.
HTTP API передаёт только команды и статистику, не видеоданные.

Папка `webtorrent-hybrid-master` изучена: версия 6.0.0 объявлена устаревшей,
а её index.js реэкспортирует WebTorrent. Используется уже установленный
WebTorrent 3.0.21 с нативным WebRTC, без установки старой ветки 2.x.

Параметры: `TORFILMS_BRIDGE_PORT` (18183), `TORFILMS_BRIDGE_RAM_MB` (256,
допустимо 32–2048). Кеш моста отдельный от кешей браузеров. Один торрент,
до восьми активных идентификаторов читателей, запрос до 16 pieces; заявки
истекают через 15 секунд. Для смены торрента пока остановите мост Ctrl+C и
запустите снова. Публичный доступ не включён; аутентификация, HTTPS для телефонов,
TURN и упаковка в приложения остаются отдельными этапами.

`/bridge/state` показывает RAM, приём/отдачу, типы соединений и предупреждения.
Интеграционный тест включается через `TORFILMS_TEST_WEBRTC=1` и требует работающего
локального WebRTC/ICE. При текущей проверке получение метаданных от обычного пира
прошло, обмен SDP прошёл, но WebRTC-передача не завершилась за 35 секунд.
После этого проверен настоящий браузер: мост принял 293431 байт тестового MP4
от uTP-источника, отдал их WebRTC-получателю, браузер воспроизвёл 10.04 секунды
до конца (readyState 4, один WebRTC-пир, RAM около 0.3 МБ). Исходный ролик был
сгенерирован FFmpeg в памяти, без видеофайла на диске. Node→Node-тест по-прежнему
не подтверждён; его пропуск по умолчанию не означает успешной WebRTC-проверки.
VPN и брандмауэр автоматически не меняются.

`npm audit` сообщает четыре high-записи из-за транзитивного `ip` и зависимых
пакетов. Не выставляйте прототип в интернет. Предлагаемый npm принудительный
откат на несовместимые старые версии не применялся.

### Браузерный P2P-прототип (без серверного RAM-кеша)

После `npm run build:p2p` откройте `/p2p/index.html` на работающем сайте.
На этом компьютере: http://127.0.0.1:18181/p2p/index.html.
Страница независима от серверного API торрентов: движок WebTorrent работает
в браузере посетителя. Полученные куски хранятся в ограниченном RAM-store и
раздаются WebRTC-пирам. Отдача ограничена выбранной скоростью. Остановка очищает
кеш и закрывает соединения. RAM-лимит не включает декодер и незавершённые запросы.

Для проверки выберите маленький MP4/H.264/AAC на первом устройстве, скопируйте
созданную magnet-ссылку на второе. Первый зритель должен оставить вкладку открытой.
Счётчики показывают число пиров, приём и отдачу. Страница использует публичные
WebSocket-трекеры для сигнализации; они видят infohash и сетевое подключение.
Доступность трекеров и соединение через NAT не гарантированы; TURN пока не настроен.

На телефоне необходим HTTPS с доверенным сертификатом: Service Worker не работает
на обычном HTTP LAN-адресе. Все файлы `public/p2p` можно разместить на статическом
HTTPS-хостинге: Node/FFmpeg этому режиму не нужны. Развёртывание HTTPS пока не выполнено.
Кеш видео не пишется в IndexedDB/Cache Storage/файлы; ОС может подкачивать память.
Регистрация Service Worker хранится браузером и ограничена путём `/p2p/`.

Ограничения: только WebRTC-источники (не обычные TCP/UDP magnet-раздачи), нет
перекодирования и универсального выбора озвучек. Это прототип, не замена прежнего
плеера. Передача между двумя реальными устройствами требует отдельной проверки.

```powershell
cd D:\ProjectTorFilms\Torfilms
npm start
```

Откройте [http://127.0.0.1:18181](http://127.0.0.1:18181).

Лимит RAM-кеша в интерфейсе можно менять от 128 МБ до 16 ГБ. Порт и стартовый лимит можно изменить:

```powershell
$env:TORFILMS_PORT = 18181
$env:TORFILMS_MEMORY_MB = 2048
npm start
```

Для внешнего воспроизведения кнопка `VLC` сначала ищет `vlc.exe` в `PATH`, затем использует `ffplay` как fallback. Пути можно задать переменными `TORFILMS_VLC` и `TORFILMS_FFPLAY`. Для выбора аудиодорожек в браузере нужны `ffmpeg.exe` и `ffprobe.exe` в `PATH`; их пути можно задать через `TORFILMS_FFMPEG` и `TORFILMS_FFPROBE`.

## Как реализована потоковая загрузка

1. WebTorrent получает метаданные и подключается к swarm.
2. `BoundedMemoryStore` заменяет файловое хранилище на RAM-кеш и ограничивает его выбранным лимитом.
3. HTTP-ответ читается по одному piece: даже запрос до конца фильма не создаёт внутреннюю подписку WebTorrent на весь файл. Чтение отменяется при закрытии соединения, в том числе во время ожидания данных или освобождения сетевого буфера.
4. При переполнении LRU вытесненный piece помечается как unverified через внутренний механизм WebTorrent и может быть загружен снова после seek.
5. `/stream/:torrentId/:fileIndex` поддерживает `Range`, что нужно для перемотки и работы VLC/HTML5.
6. `/api/tracks/:torrentId/:fileIndex` получает список audio streams через `ffprobe`; `/playback/:torrentId/:fileIndex?audio=N` отдаёт выбранную дорожку как fragmented MP4 с AAC.

## Связь с исходниками пользователя

В проектной структуре оставлены исходники `qbittorrent-5.2.3` и `vlc-master` рядом с приложением. При проектировании использованы те же концепции приоритета файлов/pieces, cache policy и Range playback:

- qBittorrent: `src/base/bittorrent`, `src/webui/api/torrentscontroller.cpp`, `src/webui/api/synccontroller.cpp`;
- VLC: public LibVLC API в `include/vlc/libvlc_media_player.h` и потоковые input/access модули.

В текущей Windows-сборке нативный qBittorrent/libVLC не компилировались автоматически: у среды не было Qt/C++ toolchain. WebTorrent + memory-chunk-store дают тот же runtime-подход без промежуточных видеофайлов; VLC подключается как внешний player через локальный RAM-only HTTP endpoint.

Используйте только торренты и видео, на которые у вас есть права.

## Проверка изменений

`npm test` проверяет точность байтовых диапазонов с ненулевым смещением файла,
отмену чтения, повтор после вытеснения из RAM, защиту от устаревшего seek,
буфер перед автозапуском и HTTP/API на отдельном сервере со свободным портом.
Тестовый сервер не использует сеансы запущенного приложения.

Медиатест требует FFmpeg/ffprobe в PATH и генерирует короткий ролик целиком в RAM.
Он воспроизводит ошибку старой команды (кадр из предыдущего GOP после seek),
проверяет правильный первый кадр новой команды, разницу стартовых меток <100 мс
и монотонный DTS обеих дорожек, а также сохранение частоты декодированных кадров
25 fps после перемотки.

При перемотке совместимый видеокодек копируется без программного кодирования.
Обе дорожки сохраняют начало от предыдущего ключевого кадра; ffprobe определяет
его положение, а плеер пропускает общий preroll перед запуском. PTS и DTS видео
не выравниваются друг относительно друга: это важно для правильного показа B-кадров.

Окно предзагрузки при транскодировании следует за реальным чтением FFmpeg.
Heartbeat плеера сообщает время, но не заменяет точное смещение приблизительным
расчётом через средний битрейт. После перемотки автозапуск ожидает три секунды
непрерывного буфера (либо остаток до конца фильма). Кнопка Play во время подготовки
не запускает кадры до выбранной позиции.

Ограничения: лимит RAM относится к кешу завершённых pieces каждого сеанса;
память Node, незавершённых pieces, FFmpeg и браузерного буфера учитывается отдельно.
Отображение torrent-кеша на шкале времени приблизительное для переменного битрейта;
буфер HTML5-плеера показывается по фактическим временным диапазонам.
Автотесты не подтверждают отсутствие слышимого рассинхрона на всех реальных
контейнерах и кодеках — это требует отдельного воспроизведения после обновления.
