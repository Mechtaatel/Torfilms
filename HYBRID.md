# Домашний Hybrid-мост и каталог

Открыть: https://192.168.0.122:18184/ (доверенный домашний сертификат).
`start-online.ps1` запускает существующий supervisor; автозапуск после входа в Windows сохраняется.

## Параллельная работа

`bridge.js` → `bridge-pool.js` запускает отдельные процессы `bridge-worker.js` по infoHash.
Несколько зрителей одной раздачи используют один процесс и общий кеш моста.
Разные фильмы / качества получают разные процессы, event loop и соединения.
При падении одного процесса остальные остаются доступны. Повторное подключение
создаёт процесс заново; RAM погибшего процесса не восстанавливается.

По умолчанию одновременно доступны 4 раздачи × 256 МБ завершённых pieces =
1024 МБ суммарного лимита кешей. Это **не** предел всей памяти: Node, WebRTC,
незавершённые pieces, FFmpeg и декодер используют дополнительную RAM.
На стороне каждого браузера остаётся собственный независимый RAM-кеш.

Параметры окружения перед запуском supervisor:

- `TORFILMS_BRIDGE_WORKERS`: 1–8, по умолчанию 4.
- `TORFILMS_BRIDGE_RAM_MB`: 32–2048 на процесс, по умолчанию 256.
- `TORFILMS_CATALOG_DIR`: папка каталога, по умолчанию `data/`.

Неиспользуемая 15 минут раздача освобождает слот. При заполнении всех слотов
новая раздача получает явную ошибку; текущие зрители не отключаются.
Чтение HTTP и запросы нужных pieces продлевают активность раздачи.
Чистая раздача ранее загруженных WebRTC-кусков без новых запросов не гарантирует
удержание серверного слота: браузеры могут продолжать обмен между собой.
До 8 одновременно активных читателей на раздачу; не более 16 pieces в одном запросе.
Ограничение отдачи каждого процесса — 4 МиБ/с, всего до 16 МиБ/с при четырёх раздачах.
Это параллелизм независимых раздач, не разделение одного видео между CPU-процессами.
Скорость одной раздачи по-прежнему зависит от сидов, сети и обработки кодеков.
Состояние: `/bridge/state`, настройки: `/bridge/config`.

## Каталог

Главная страница: сетка обложек, категории, поиск и добавление карточек.
Карточка имеет адрес `/film/tt1727587` с IMDb ID; название и описание вводятся
вручную, импорт базы IMDb не выполняется. Каталог изначально пустой.
Обложка — HTTPS-ссылка либо загруженный JPEG/PNG/WebP до 2 МБ.
Можно сохранить до 12 версий фильма: подпись качества, magnet либо .torrent
до 3 МБ, индекс видеофайла (с 0). Сами видео на диск не записываются.
Карточки и метаданные .torrent сохраняются в `data/catalog.json`; этот файл
нужно включить в резервную копию. Конфликт одновременного редактирования обнаруживается.

Плеер встроен в карточку фильма. В карточке нажмите «Смотреть»;
выбор качества есть также внутри плеера. Переключение подключает другой torrent
и начинает воспроизведение с начала, без остановки чужих раздач.
Поддерживаемый аудиокодек копируется, несовместимый преобразуется мостом в AAC.
Существующие ограничения браузерных видеокодеков не изменены.

Каталог рассчитан на доверенную домашнюю сеть: любой её пользователь может
добавлять и редактировать карточки. Авторизации и квот пользователей пока нет.
Не публикуйте сервер в интернете без отдельной защиты.

## Проверки

`npm test` включает передачу двух синтетических раздач одновременно из локального
TCP/uTP-источника через независимые процессы и HTTP RAM-потоки, маршрутизацию
WebSocket tracker через LAN-прокси, повторное использование процесса, лимиты,
падение одного процесса и сохранность второй раздачи, сохранение .torrent и карточек.
Это не заменяет проверку воспроизведения и качества связи на Android.
Полный Node→WebRTC-тест включается отдельно: `TORFILMS_TEST_WEBRTC=1`.

## Восстановление передачи

Плеер получает метаданные у моста до подключения RTC. Если RTC не отдаёт
нужный piece, браузер запрашивает именно этот piece по HTTPS, проверяет SHA-1
и помещает его в тот же ограниченный RAM-кеш. Затем он объявляет HAVE своим
WebRTC-пирам: обмен между зрителями сохраняется. Объём резервной передачи
отдельно виден в статистике. Это не запись видео в файл и не перекодирование.

Рабочие процессы проверяются каждые 5 секунд. Три таймаута подряд приводят
к замене только зависшего процесса и повторному подключению его раздачи.
После такого зависания нативная RTC-часть этого процесса отключается до
перезапуска главного сервера: куски идут сервер → браузер по HTTPS,
а браузер → браузер по WebRTC. Новое подключение холодной magnet-раздачи
всё ещё требует доступных пиров и получения метаданных.

На Windows резервная схема теперь используется по умолчанию: нативные
RTC-соединения сервера отключены, поскольку они воспроизводимо зависали.
Экспериментальное включение: `TORFILMS_BRIDGE_NATIVE_RTC=1`.
P2P-соединения между браузерами этим параметром не отключаются.
